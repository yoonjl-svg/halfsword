# 붉은 회랑 짓기 멈칫 고침 (2026-10-17)

봉인의 중정 디자인 리뷰(헤드리스 SwiftShader 측정, `tools/browser/courtyard_review.mjs --modes=cost`)에서 붉은 회랑(`loggia`, 여정 4판)을 짓는 데 약 4.7 s, 다른 무대는 0.2~0.7 s 로 나왔다. 밤의 붉은 회랑(`loggia_night`, 9판)도 낮 무대를 그대로 지은 뒤 덧붙이므로 같이 느렸다(3.8 s).

## 원인
- 결투장 바닥 무늬 `pavingTexture` (1024×1024 캔버스): 판석 · 결 · 고리 · 나침반 · 양각 · 글자 띠까지 그리기 명령 약 2,600 개를 기본(가속) 2D 캔버스에 쌓은 뒤, ⑥ 긴 오후 그림자를 굽느라 `getImageData` 로 화소 전체를 되읽는다.
- 가속 캔버스는 그리기 명령을 미뤄 두었다가 읽는 순간 GPU 에서 한꺼번에 그리고, 끝날 때까지 기다린다. 헤드리스는 GPU 가 소프트웨어(SwiftShader)라 이게 오래 걸린다.
- CPU 프로파일(한 번 짓기 5.68 s): `getImageData` 한 줄이 5.31 s. 화소 계산(JS) 0.06 s, 꼴 짓기 · 합치기 · 빛 굽기를 다 합쳐도 0.3 s.
- 나눠 재기(같은 코드를 페이지에서 따로 돌림): 명령을 쌓는 데 수 ms, 읽는 순간 GPU 에서 그리기 1.6~2.0 s, 4 MB 되읽기 자체는 15~20 ms. 같은 명령을 CPU 캔버스에 그리면 되읽기 · 화소 계산까지 0.09~0.13 s.
- 숫자가 판마다 2.9~4.7 s 로 흔들린 까닭: 이 동기 호출이 바로 앞까지 그린 게임 프레임의 GPU 일(헤드리스는 한 프레임에 수백 ms)까지 함께 기다렸다. 그리기를 멈추고 GPU 가 쉴 때 재면 1.35 s.
- 다른 무대에는 화소를 되읽는 캔버스가 없다. 다른 캔버스 질감은 warm 때 GPU 로 올라가면서 그려진다.

## 고친 것
- 그 캔버스 하나만 `getContext('2d', { willReadFrequently: true })` (CPU 캔버스)로 그린다. `src/stage_kit.js` `canvasTex(w, h, draw, attrs)` 에 넷째 인자를 더했다(안 주면 지금과 같음, 다른 무대는 그대로). 대기실(`lobby.js`)도 되읽는 캔버스를 같은 방식으로 만든다.
- 그리기 명령 · 순서 · 난수 · 그림자 화소 계산은 한 줄도 안 바꿨다. 하늘 · 회반죽 · 깃발 캔버스는 되읽지 않으므로 그대로 뒀다.
- 충돌 · 결투장 · 물리와는 상관없다(그림만 짓는 곳).

## 전/후 (헤드리스 SwiftShader, 844×420, 빌드판)
그리기를 멈추고 GPU 가 쉴 때 `game.setStage` 를 잼 (한 페이지 여섯 무대 다섯 바퀴, 첫 바퀴 빼고 중앙값, ms):

| 무대 | 짓기 전 → 후 | warm 전 → 후 | setStage 전체 전 → 후 | + GPU 일 끝까지 전 → 후 |
|---|---:|---:|---:|---:|
| 붉은 회랑 | 1351 → **297** | 180 → 156 | 1533 → **458** | 2052 → 1013 |
| 밤의 붉은 회랑 | 1405 → **291** | 187 → 168 | 1593 → **468** | 2139 → 948 |
| 성 안뜰 (견줌) | 126 → 133 | 137 → 144 | 267 → 279 | 755 → 765 |
| 대성당 (견줌) | 204 → 205 | 202 → 197 | 408 → 404 | 1363 → 1336 |

- 마지막 칸: setStage 가 끝난 뒤 1 화소 `readPixels` 로 기다린 데까지 (warm 이 GPU 에 맡기고 나온 첫 그림 · 질감 그리기까지).
- 리뷰와 같은 도구(`courtyard_review.mjs --modes=cost`)의 짓기 시간: 붉은 회랑 2873 → 276, 밤 1782 → 270.
- GPU 에 앞 일이 남은 채로 재면(무대를 잇달아 바꾸거나 프레임을 그리는 중에) 짓기는 2758~4454 → 304~345. 다만 이때는 고친 판의 warm 이 길어 보인다(0.2~1.5 s). 남은 GPU 일을 이번에는 warm 의 첫 셰이더 확인 호출이 떠안기 때문이다(전에는 짓기의 `getImageData` 가 떠안았다). 그래도 setStage 전체는 2951~4710 → 1649~1892.
- 그리기 양은 같다 (상대 고정): 붉은 회랑 호출 269 · 삼각형 112,551 · 꼴 148 · 무늬 11 · 셰이더 29 · 무대 무늬 7.09 MB. 밤 293 · 111,435 · 169 · 14 · 31 · 7.23 MB.

## 그림 견주기
같은 빌드 주소 · 같은 가짜 시계 · AI 멈춤으로 찍었다. 카메라 일곱(경기 카메라, 넓은 각 둘, 바닥 높이, 위, 낮게 스치는 각, 무대만) × 낮 · 밤 = 14 장. 값은 255 단계 기준이다.
- 밤 (같은 판을 두 번 찍으면 0 차 — 완전히 결정적): 평균 절대차 0.06~0.19, 최대 3~8, 2 단계 넘는 화소 0.002~0.65 %, 8 단계 넘는 화소 0, PSNR 54~60 dB.
- 낮: 평균 0.07~0.22, PSNR 50.7~59 dB. 8 단계 넘는 화소는 고정 카메라에서 장마다 1~7 개, 모두 두 사람 둘레다. 경기 카메라에서는 0.11 % 인데, 이것은 같은 판을 두 번 찍어도 나오는 두 사람 자세 떨림(0.11 %)과 같은 크기다.
- 질감 자체: 1 단계 이상 다른 화소 62 %, 2 넘게 15 %, 8 넘게 0.39 % (최대 24 — 판석 이음매 · 글자 가장자리의 안티에일리어싱), 평균 밝기 −0.2 단계.
- 판정: 눈으로 구별되지 않는다. GPU 래스터와 CPU 래스터의 가장자리 처리 차이이고, 원래 기기 · 브라우저마다 다른 종류의 차이다.

## 새는 것
- 붉은 회랑 → 성 안뜰 → 밤의 붉은 회랑 → 대성당 → 붉은 회랑 → 산호 항구를 다섯 바퀴 돌았다. 꼴 · 무늬 · 셰이더 · 무대 메쉬 수가 바퀴 1 과 바퀴 4 에서 같고 고치기 전과도 같다. 힙(gc 뒤)은 37.1 → 36.7 MB, 오류 0.
- `round3_check.mjs` ③ 오가기(열한 곳 × 네 바퀴, 밤의 붉은 회랑을 더함): 통과, 전/후 같은 수. 도구 자체는 ① 자료 단언('etna_night 는 여정 순서 밖' — 10/17 여정 순서가 바뀐 뒤 낡음)에서 먼저 멈춰, ③ 만 떼어 돌렸다. 도구는 손대지 않았다.

## 참고
- 실기기(아이폰 17e)에서는 재지 못했다. 헤드리스는 캔버스 GPU 래스터와 셰이더 컴파일이 크게 부풀려지므로, 실기기의 전 판 멈칫은 이보다 훨씬 작았을 수 있다. 고친 판에는 GPU 기다림이 없고 CPU 로 그리는 비용(헤드리스 약 0.1 s)만 남는다.
- 헤드리스에서 무대 바꾸기 시간을 잴 때: 프레임을 그리는 중이면 첫 동기 GL 호출이 앞 프레임 일을 떠안는다. `game.renderCap.tick = () => false` 로 그리기를 멈추고 잠깐 기다린 뒤 재야 무대끼리 견줄 수 있다. `gl.finish()` 는 기다리지 않았다(0 ms). 진짜로 기다리려면 1 화소 `readPixels` 를 쓴다.
- 붉은 회랑 무대 무늬 7.1 MB (1024² 바닥이 5.3 MB) — 다른 무대(1.3 MB)보다 크지만 그림이 바뀌므로 이번에는 그대로 뒀다.
